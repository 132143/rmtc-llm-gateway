# 交接给队友（含"用 LLM 合并两边项目"的操作指南）

> 目标：你（或你队友的 LLM）能在**不读全部源码**的前提下，判断哪些该保留、哪些可以替换，
> 并且合并后不会破坏协议合规与已经验证过的东西。

## 0. 一分钟定位

| 目录 | 是什么 | 能不能随便改 |
|---|---|---|
| `rmtc_gateway/` | 本地/自建 OpenAI 兼容网关（协议 §5 的另一种实现，练习用） | 可改；正式赛**不能用**它替代官方网关 |
| `rmtc_client/` | 调 AI 的客户端：超时/降级/预算/JSON 修复/事件理解 | 谨慎改：额度与降级逻辑踩过坑 |
| `contestant/` | **比赛主体**：感知→动作、策略、ROS 节点、模拟器 | 主要改这里（策略） |
| `tests/` | 102 个测试，覆盖网关/客户端/参赛代码 | 合并后必须全绿 |
| `docs/` | 协议对照、真机记录、实验数据、移植性、封存参数 | 只读参考 |
| `scripts/` | 调参与打包脚本（`gen_maps.py`、`gen_stage2.py`、`cost.py`…） | 可改 |
| `scripts/vm/` | 只在我们虚拟机里用的一键对局脚本 | **开发用**，比赛不需要 |

入口只有两个：
- 比赛：`python3 -m contestant.bot_node --seat <席位> --stage 2`
- 本地网关：`python3 -m rmtc_gateway --port 8000`

## 1. 合并前先跑（3 条命令，两个系统都跑一遍）

```bash
python run_tests.py                                   # 应 102 通过
python -m rmtc_gateway --port 8011 &                  # 起网关
curl -s http://127.0.0.1:8011/healthz                # 应 {"status":"ok",...}
```

Windows 上 `bot_node` 起不来是正常的（没有 rclpy），只跑测试即可。

## 2. 必须保留的"不能破"清单（协议级）

| 项 | 具体要求 | 破了会怎样 |
|---|---|---|
| 话题名 | `/team_<席位>/perception`、`/team_<席位>/action`、`/team_<席位>/registration` | 收不到/发不出 |
| QoS | 感知/动作 RELIABLE + VOLATILE + KEEP_LAST(1)；注册加 TRANSIENT_LOCAL | 静默收不到 |
| 动作字段 | `tick`(int) + `session_id`(str) 原样回填；动作/方向全小写 | E_SCHEMA / E_TICK |
| 去重 | 同一 Tick 重发不重复决策；旧帧丢弃 | 重复推进策略 |
| 换场次 | 新 `session_id` 清空定位/记忆/在途 AI | 用上一场的结果 |
| 阵亡/保护 | 阵亡只能 WAIT；出生保护期内不 ATTACK | E_STATE 扣 invalid_actions |
| AI 资格 | 第二阶段每场至少 1 次**本场本席位真实成功调用**（我们靠心跳兜底） | 任务分 M=0，直接少 15 分 |
| AI 额度 | 每场 100；按"发出的请求"计数（超时也算） | 提前耗尽，事件理解没了 |
| 事件理解 | 必须由 LLM 判断，禁止正则/关键词/模板 | P5 违规 |
| 路径 | 不许出现绝对路径/写死令牌/写死地图尺寸 | 换机/换场就废 |

## 3. 已经用数据验证过、建议直接保留的部分

| 决策 | 数据 | 结论 |
|---|---|---|
| 策略 = BFS 贪心 + 记忆（vs 蛇形） | 第一阶段 9 张图：40/40 vs 8/40 | 保留贪心 |
| `strategy_detour = 0` | 24×24：0→47.5、6→47.5、20→40.0；18×18：0 与 6 相同 | 保留 0 |
| 战斗模式 = hybrid | 正式节奏：45.0(hybrid) > 42.0(opportunistic) > 30.0(never) | 保留 hybrid 为默认 |
| `mission_max_distance = 8` | 24×24：45.0→52.5；18×18 无变化 | 保留 8 |
| 空闲巡逻 | 等待 300→10，但分数 47.5 vs 50.0、更易掉血 | **默认关闭**（代码保留） |
| aggressive（主动追人） | 42.5 vs hybrid 45.0 | 不采用 |
| `resource_first`（先采集再打） | 资源被堵的图上更差 | 仅作对照保留 |
| JSON 模式 + 修复 | 5/5 合法；坏 JSON 有 6 类修复策略 | 保留 |
| 超时 4s、预算按请求计 | 超时也吃额度；真实延迟最大 2.7s | 保留 |

## 4. 合并时最容易犯的三个错

1. **把"能跑"当"合规"**：练习端 mock 的成功调用不算正式 AI 资格；
2. **把"练习分数"当"正式分数"**：练习包的 `rules.txt` 是 v1.0（伤害 300 封顶），
   官方规则 v1.1 是 **500**，同一局面练习能高 5 分；
3. **两边都用 env 切策略**：规则 §2.3 现场只允许改 `decision_config.json` 的 `decision_type`，
   所以策略必须能靠一个枚举切换（我们登记了 `collect/balanced/combat`）。

## 5. 给"另一个 LLM"的比对建议顺序

1. 先读 `PROJECT_MANIFEST.json`（模块、入口、接口、测试、实测结论都在里面）；
2. 用 `docs/CONTESTANT_MAP.md` 做协议条款对表，**两边谁缺条款就补谁**；
3. 用 `tests/` 做回归基线：合并后先让 102 个测试全绿，再谈性能；
4. 只在"策略/决策"层面比较优劣（`contestant/strategy.py`、`contestant/agent.py`），
   接口层（QoS、字段、回填）不要各写一套；
5. 任何改动都要能回答："哪条规则/哪次实测支撑这个改动？"
